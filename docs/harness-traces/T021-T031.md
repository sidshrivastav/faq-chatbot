# Harness Trace: T021-T031 FAQ Source Management

## Task Scope

- T021: API contract tests for FAQ source list, create, detail, update, and delete.
- T022: Representative harness trace task for activation/deactivation conflict handling.
- T023: Service tests for readiness and invalid entries.
- T024: Frontend tests for source list states.
- T025-T031: FAQ source schemas, repository, service transitions, admin routes, source list/detail screens, and frontend service functions.

## Brainstorm

- Keep source management state in a repository boundary so later SQLite persistence can replace the in-memory implementation without changing routes.
- Keep route handlers thin: authorization and HTTP adaptation in FastAPI, source lifecycle rules in `SourceService`.
- Model readiness separately from lifecycle status so an invalid source can be created and reviewed without being activated.
- Enforce one active source per use case by deactivating the previous active source during activation.
- Render admin source states with text labels in addition to visual badges so status is not color-only.

## test-writer Output

Test plan generated before implementation:

- Happy path: admin creates, lists, retrieves, updates, activates, deactivates, archives, and deletes a FAQ source.
- Validation failures: missing required source name, use case, or entry answer text should be rejected by schemas/API validation.
- Authentication failures: missing local auth headers should be rejected by existing auth dependencies.
- Authorization failures: end-user role receives `403` for admin FAQ source routes.
- Not-found cases: missing source IDs return the shared not-found error shape.
- Activation conflict: activating a ready source deactivates any previous active source in the same use case.
- Invalid/no-entry behavior: empty source remains creatable for admin review but cannot be activated.
- Duplicate question behavior: duplicate entries produce warning readiness.
- Frontend states: ready, empty, loading, invalid-source, error, and detail action states render deterministic text.
- Mocking strategy: no external services are used; frontend service tests mock `fetch`.
